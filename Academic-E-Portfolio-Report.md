**Skills Developed:**
- Python programming proficiency
- Algorithm analysis and complexity theory
- Data visualization
- Performance optimization techniques

**Code Sample:**
```python
def bubble_sort(list_to_sort):
    n = len(list_to_sort)
    for i in range(n):
        for j in range(0, n-i-1):
            if list_to_sort[j] > list_to_sort[j+1]:
                list_to_sort[j], list_to_sort[j+1] = list_to_sort[j+1], list_to_sort[j]
```

#### 3.2.2 Technical Architecture

**Core Components:**

#### 3.2.3 Design Principles Applied

**SOLID Principles:**

1. **Single Responsibility Principle (SRP)**
   - Each class has a well-defined, single purpose
   - BankAccount handles account operations exclusively
   - Exceptions are separated into dedicated module

2. **Open/Closed Principle (OCP)**
   - System designed for extension without modification
   - Observer pattern placeholder for future notification features
   - Facade pattern placeholder for simplified interfaces

3. **Liskov Substitution Principle (LSP)**
   - Consistent behavior across inheritance hierarchies
   - Exception hierarchy maintains expected behavior

4. **Interface Segregation Principle (ISP)**
   - Clients depend only on methods they use
   - Clear, minimal interfaces for banking operations

5. **Dependency Inversion Principle (DIP)**
   - High-level modules independent of low-level details
   - Abstraction-oriented design for flexibility

**Design Patterns:**

- **Observer Pattern** (planned extension): For account activity notifications
- **Facade Pattern** (planned extension): For simplified client interfaces
- **Defensive Programming**: Input validation and comprehensive error handling

#### 3.2.4 Thread Safety and Concurrency

**Challenge:**  
Banking systems must handle concurrent transactions safely to prevent race conditions, data corruption, and inconsistent state.

**Solution Implementation:**

1. **Lock-Based Synchronization**
   - Each `BankAccount` instance has a dedicated `threading.Lock`
   - All state-modifying operations acquire the lock before execution
   - Automatic lock release ensures safety even during exceptions

2. **Deadlock Prevention**
   - Consistent lock ordering in transfer operations
   - Locks acquired in ascending order of account identifiers
   - Eliminates circular wait conditions

3. **Atomic Operations**
   - Balance checks and updates performed atomically
   - Prevents TOCTOU (Time-of-Check-Time-of-Use) vulnerabilities

**Code Example:**
```python
class BankAccount:
    def __init__(self, account_id, initial_balance=0):
        self._account_id = account_id
        self._balance = initial_balance
        self._lock = threading.Lock()
    
    def deposit(self, amount):
        if amount <= 0:
            raise InvalidAmountError("Deposit amount must be positive")
        with self._lock:
            self._balance += amount
    
    def withdraw(self, amount):
        if amount <= 0:
            raise InvalidAmountError("Withdrawal amount must be positive")
        with self._lock:
            if self._balance < amount:
                raise InsufficientFundsError("Insufficient funds for withdrawal")
            self._balance -= amount
```

2. **Error Handling**
